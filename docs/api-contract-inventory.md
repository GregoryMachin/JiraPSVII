# JiraPS API Contract Inventory

## Purpose

This inventory maps every exported JiraPS function to its current HTTP contract, deployment differences, data conventions, authorization needs, output conversion, and automated coverage.
It records the implementation as it exists on 27 July 2026 rather than presenting planned routes as completed work.

The inventory is a migration control for the Cloud v3 work in `Project/Project.md`.
Any API-affecting change must update the relevant row together with its source, tests, help, and changelog.

## Status and scope conventions

| Label | Meaning |
|---|---|
| Current | The implemented contract is intentionally current or the command is local-only. |
| Legacy Cloud v2 | Cloud currently uses a v2 route that needs operation-level v3 review. |
| Deprecated | Atlassian has deprecated or replaced the implemented Cloud operation. |
| Unverified | The current API, permission, scope, response, or live behavior still needs confirmation. |
| Transport | The command is a generic transport surface whose contract is selected by its caller. |

No exported JiraPS command currently uses an experimental Atlassian endpoint.
If experimental support is introduced, it must be opt-in and explicitly labelled here.

OAuth is not yet implemented by JiraPS.
The scope column records the narrowest current classic scope identified during this audit and marks granular-scope confirmation as unverified.
`Unverified` is a delivery blocker for the later OAuth release, not permission to request a broad scope silently.

`Local` means that the function itself makes no Jira request.
`Indirect` means that it obtains data through another inventoried JiraPS command.
Routes containing `{id}`, `{key}`, or another placeholder describe the operation family rather than literal interpolation syntax.

## Inventory findings

### Immediate Cloud migration priorities

1. Direct issue reads and many issue subresources still use Cloud v2 even though writes and JQL search already split to v3.
2. User, group, filter, metadata, version, component, link, watcher, worklog-read, and attachment operations need endpoint-by-endpoint v3 or current-contract confirmation.
3. `Get-JiraStatus` uses the floating `/rest/api/latest` alias and needs explicit deployment-aware version selection.
4. Generic absolute attachment, pagination, and remote-link URLs need trusted-host and authorization-forwarding tests.

### Coverage gaps

The following API operations have unit tests but no direct live integration coverage:

- filter permissions;
- remote links;
- group creation, removal, and membership mutation;
- version movement;
- user creation, update, and removal;
- issue-label updates.

Destructive administrative canaries must use disposable users, groups, projects, filters, issues, and links.
They must not run against production tenants or persist personal data in artifacts.

### Identity, content, and permission risks

- Cloud identity must remain `accountId`; Data Center identity remains username or name.
- Issue, comment, worklog, attachment, filter, user, group, and permission results are sensitive.
- Cloud ADF and Data Center text/wiki representations must stay behind deployment-aware adapters.
- Permissions and OAuth scopes must be tested against least-privilege accounts rather than only site administrators.
- Classic OAuth scopes in this inventory are provisional.
  Granular scopes must be verified from the selected current endpoint before OAuth support is released.

## Maintenance rules

- Add a row in the same change that exports a new public function.
- Remove a row only in an approved breaking release that also removes the export.
- Keep source, unit-test, and integration-test links relative to this file so the inventory test can validate them.
- Mark unsupported, deprecated, experimental, or unverified behavior explicitly.
- Do not replace an `Unverified` label with `Current` until the official contract, permission, scope, fixtures, and applicable live test have been reviewed.
- Never place tenant URLs, account IDs, issue data, authorization headers, cookies, API tokens, or OAuth tokens in this inventory.
