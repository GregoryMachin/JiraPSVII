# Authentication

## about_JiraPSVII_Authentication

# SHORT DESCRIPTION

JiraPSVII supports multiple authentication methods: HTTP basic authentication,
API tokens (Jira Cloud), Personal Access Tokens (Jira Data Center),
caller-supplied OAuth access tokens (Jira Cloud), OAuth client credentials
(Jira Cloud automation), and session-based authentication.

# LONG DESCRIPTION

JiraPSVII supports the following authentication methods:

* HTTP basic authentication - username and password
* API tokens - for Jira Cloud (email + token)
* Personal Access Tokens (PAT) - for Jira Data Center (bearer token)
* OAuth access tokens - for Jira Cloud, supplied by an external token broker
* OAuth client credentials - for non-interactive Jira Cloud service accounts and backend automation
* Session-based authentication - creates a persistent session for subsequent commands

> Be sure to set JIRA up to use HTTPS with a valid SSL certificate if you are
> concerned about security!

## HTTP Basic

Each JiraPSVII function that queries a Jira instance provides
a `-Credential` parameter.
Simply pass your Jira credentials to this parameter.

```powershell
$cred = Get-Credential 'powershell'
Get-JiraIssue TEST-01 -Credential $cred
```

> HTTP basic authentication is not a secure form of authentication.
> It uses a Base64-encoded String of the format "username:password"
> and passes this string in clear text to Jira. Because decrypting this
> string and obtaining the username and password is trivial,
> the use of HTTPS is critical in any system that needs to remain secure.

## API Token (Jira Cloud)

API tokens are generated by the user or service account for authenticating
against Jira Cloud. Scoped API tokens are recommended because they limit the
Jira APIs the token can call.

> As of December 1st 2018, Atlassian requires API authentication
> with Jira Cloud to always use API Tokens.
> More information in the [Deprecation notice](https://developer.atlassian.com/cloud/jira/platform/deprecation-notice-basic-auth-and-cookie-based-auth/).

JiraPSVII provides first-class support for API tokens via `New-JiraSession`:

```powershell
# Interactive prompt
$token = Read-Host -AsSecureString "Enter your API Token"
New-JiraSession -ApiToken $token -EmailAddress "you@example.com"
```

The API token and email are combined into a Basic authentication header
as required by Jira Cloud's API.

For scoped API tokens, also provide `-CloudId`. JiraPSVII then routes calls through
`https://api.atlassian.com/ex/jira/{cloudId}`, which is the Atlassian gateway
route used by scoped Jira API tokens.

```powershell
New-JiraSession -ApiToken $token `
    -EmailAddress "you@example.com" `
    -CloudId '11223344-a1b2-3b33-c444-def123456789'
```

JiraPSVII cannot inspect an API token to prove which scopes were selected. Jira
Cloud enforces token scopes and Jira permissions when each request is made. For
scope guidance by command family, see `about_JiraPSVII_ApiTokenScopes`.

More information on API tokens and how to create one:
https://confluence.atlassian.com/cloud/api-tokens-938839638.html

## Personal Access Token (Jira Data Center)

Personal Access Tokens (PATs) are used for authenticating against
Jira Data Center (on-premise) installations.

JiraPSVII provides first-class support for PATs via `New-JiraSession`:

```powershell
# Interactive prompt
$pat = Read-Host -AsSecureString "Enter your PAT"
New-JiraSession -PersonalAccessToken $pat
```

The `-PersonalAccessToken` parameter also accepts the aliases `-PAT` and `-BearerToken`.
The PAT is sent as a Bearer token in the Authorization header.

More information on PATs for Data Center:
https://confluence.atlassian.com/enterprise/using-personal-access-tokens-1026032365.html

## OAuth Access Token (Jira Cloud)

JiraPSVII accepts an OAuth access token that an external authorization or token broker has already obtained.
The token must be a `SecureString`, and the Jira Cloud site must be identified by its UUID Cloud ID.

```powershell
$accessToken = Read-Host -AsSecureString "Enter the OAuth access token"
New-JiraSession -OAuthAccessToken $accessToken `
    -CloudId '11223344-a1b2-3b33-c444-def123456789'
```

JiraPSVII constructs `https://api.atlassian.com/ex/jira/{cloudId}` and sends the token only in the `Authorization: Bearer` header.
OAuth routing is restricted to HTTPS on `api.atlassian.com`, and authentication-token query parameters are rejected.
If `-Headers` also contains `Authorization`, the explicit `-OAuthAccessToken` value takes precedence.

This parameter set does not implement interactive authorization, authorization-code exchange, or token refresh.
The caller remains responsible for obtaining a valid token with appropriate Jira scopes and replacing it when it expires.

## OAuth Client Credentials (Jira Cloud Automation)

For backend processes, scheduled jobs, and service-account automation, use the OAuth client-credentials parameter set.
It does not open a browser, require user sign-in, or prompt for consent at runtime.

```powershell
$clientSecret = ConvertTo-SecureString -String $env:JIRA_OAUTH_CLIENT_SECRET -AsPlainText -Force
New-JiraSession `
    -OAuthClientId $env:JIRA_OAUTH_CLIENT_ID `
    -OAuthClientSecret $clientSecret `
    -OAuthSiteUrl 'https://example.atlassian.net'
```

JiraPSVII exchanges the client ID and client secret at `https://auth.atlassian.com/oauth/token`, discovers accessible resources through `https://api.atlassian.com/oauth/token/accessible-resources`, selects a Jira Cloud resource, and routes Jira API calls through `https://api.atlassian.com/ex/jira/{cloudId}`.
Access tokens are short-lived and are renewed in memory before expiry.
Client secrets and access tokens are not written to JiraPSVII configuration.

The OAuth app must have Jira scopes and tenant/project access for the operations being automated.
Authentication success does not guarantee that the app can browse a specific project or issue; Jira may still return authorization or not-found responses when app access, project permissions, issue security, or scopes are insufficient.

### Discovering and selecting an accessible Jira site

Use `Get-JiraOAuthResource` to retrieve the sites and Cloud IDs represented by a caller-supplied token.

```powershell
$sites = Get-JiraOAuthResource -OAuthAccessToken $accessToken
$site = Get-JiraOAuthResource -OAuthAccessToken $accessToken -SiteUrl 'https://example.atlassian.net'
$site | New-JiraSession -OAuthAccessToken $accessToken
```

The command returns `AtlassianPSVII.JiraPSVII.OAuthResource` objects whose `CloudId` property binds to `New-JiraSession -CloudId` by property name.
When more than one site is returned, select explicitly by Cloud ID or site URL.
Display-name selection is accepted only when exactly one resource has that name; names are never used to construct request routes.

Validated site metadata is cached for 15 minutes for the current OAuth session.
Explicit-token calls always refresh the metadata, `-BypassCache` refreshes the current session, and `Clear-JiraCache -Type OAuthResources` removes it.
Access tokens and authorization headers are never cached.

## Automation and CI/CD

For scripts, CI/CD pipelines, or other non-interactive scenarios,
you need to create SecureStrings programmatically instead of using `Read-Host`.

### From Environment Variables

The recommended approach for CI/CD - store secrets in environment variables:

```powershell
# Jira Cloud with API Token from environment variable
$token = ConvertTo-SecureString -String $env:JIRA_API_TOKEN -AsPlainText -Force
New-JiraSession -ApiToken $token -EmailAddress $env:JIRA_EMAIL

# Jira Data Center with PAT from environment variable
$pat = ConvertTo-SecureString -String $env:JIRA_PAT -AsPlainText -Force
New-JiraSession -PersonalAccessToken $pat

# Jira Cloud with an externally supplied OAuth access token
$oauthToken = ConvertTo-SecureString -String $env:JIRA_OAUTH_ACCESS_TOKEN -AsPlainText -Force
New-JiraSession -OAuthAccessToken $oauthToken -CloudId $env:JIRA_CLOUD_ID

# Jira Cloud service-account automation with OAuth client credentials
$clientSecret = ConvertTo-SecureString -String $env:JIRA_OAUTH_CLIENT_SECRET -AsPlainText -Force
New-JiraSession -OAuthClientId $env:JIRA_OAUTH_CLIENT_ID -OAuthClientSecret $clientSecret -OAuthSiteUrl $env:JIRA_CLOUD_URL
```

### From a String Variable

If you have the token in a variable (be careful with secrets in memory):

```powershell
$tokenPlainText = "your-api-token-here"
$token = ConvertTo-SecureString -String $tokenPlainText -AsPlainText -Force
New-JiraSession -PersonalAccessToken $token
```

### Creating Credentials Programmatically

For `-Credential` parameter with username/password:

```powershell
$username = "jira-user"
$password = ConvertTo-SecureString -String $env:JIRA_PASSWORD -AsPlainText -Force
$credential = [PSCredential]::new($username, $password)

New-JiraSession -Credential $credential
```

Security Note: Avoid hardcoding secrets in scripts. Use environment variables,
secret managers (Azure Key Vault, AWS Secrets Manager, HashiCorp Vault),
or CI/CD secret storage (GitHub Secrets, GitLab CI Variables).

## Jira Cloud vs. Data Center

JiraPSVII automatically detects whether your Jira instance is Cloud or
Data Center/Server by calling the `/serverInfo` endpoint (see
`Get-JiraServerInformation`). This detection is cached for the session.
If you configure JiraPSVII from an AtlassianPSVII.Configuration server entry with explicit `DeploymentType` metadata, JiraPSVII uses that metadata before auto-detection.
If auto-detection fails and no explicit metadata is available, JiraPSVII raises an actionable error instead of assuming Server.

On **Jira Cloud**, JiraPSVII adapts its behavior:

* Uses `accountId` instead of `username` for user identification
  (required since Atlassian's GDPR changes removed usernames from Cloud)
* Uses API v3 endpoints for JQL search (`/rest/api/3/search/jql`)
  with token-based pagination
* Warns when `New-JiraSession` is used, since cookie-based sessions
  are deprecated on Cloud — use `-Credential` with individual commands instead
* Handles HTTP 429 (rate limiting) with automatic retry and exponential backoff

No changes are required in your scripts. JiraPSVII selects the correct
API behavior based on the explicit or detected deployment type.

## Sessions

JiraPSVII supports persistent sessions that store authentication for subsequent commands.
Once a session is created, you do not need to pass credentials to each command.

### Creating a Session

Choose the method that matches your Jira deployment:

- Jira Cloud: Use `-ApiToken` with `-EmailAddress`
- Jira Cloud OAuth: Use `-OAuthAccessToken` with `-CloudId`
- Jira Cloud automation OAuth: Use `-OAuthClientId` with `-OAuthClientSecret`
- Jira Data Center: Use `-PersonalAccessToken` (aliases: `-PAT`, `-BearerToken`)
- Either (legacy): Use `-Credential`

```powershell
# Jira Cloud
New-JiraSession -ApiToken $token -EmailAddress "you@example.com"

# Jira Cloud OAuth token supplied by an external broker
New-JiraSession -OAuthAccessToken $oauthToken -CloudId $cloudId

# Jira Cloud OAuth client credentials for backend automation
New-JiraSession -OAuthClientId $clientId -OAuthClientSecret $clientSecret -OAuthSiteUrl 'https://example.atlassian.net'

# Jira Data Center
New-JiraSession -PersonalAccessToken $pat

# Either
New-JiraSession -Credential $cred
```

Once you have created a session, you are done!
You do not need to specify credentials when running other commands - JiraPSVII will
manage this session internally.

The session is stored in the module's runtime.
This means that it will not be available in a new PowerShell session
or if the module is reloaded.

### Custom Headers

For advanced scenarios, you can also pass custom non-authentication headers:

```powershell
$headers = @{ 'X-Correlation-ID' = $correlationId }
New-JiraSession -Headers $headers
```

## OAuth Authorization-Code and Interactive Flows

Jira Cloud supports OAuth 2.0 Three-Legged OAuth (3LO) for user-delegated access,
which is appropriate for integrations that act on behalf of Jira users.

JiraPSVII does not implement interactive authorization-code, browser callback, or user-consent flows.
Use `-OAuthClientId` and `-OAuthClientSecret` for non-interactive service-account automation, or use an external broker and pass the resulting token through `-OAuthAccessToken`.
